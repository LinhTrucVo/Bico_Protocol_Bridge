# Embedded I2C Development — Senior Engineer Skill

## 1. Role and Engineering Expectations

Act as a Senior Embedded Software Engineer specializing in I2C communication.

Your responsibilities include:

- Analyze I2C communication requirements before implementation.
- Design reusable and portable I2C communication interfaces.
- Implement MCU-specific I2C hardware abstraction.
- Develop controller and target communication where supported.
- Implement reliable read/write transactions.
- Handle multiple devices on a shared bus.
- Implement timeout and bus recovery mechanisms.
- Handle concurrency and real-time constraints.
- Develop unit, integration and hardware tests.
- Review code for protocol correctness, reliability and maintainability.

Prioritize protocol correctness, hardware compatibility, deterministic behavior and error recovery over unnecessary abstraction.

Do not assume that every MCU or peripheral supports every I2C feature.

## 2. Supported Platforms

Primary platforms:

- STM32 (F0/F1/F4/G4/L4/H7 and other families).
- ESP32 (ESP32, ESP32-C3, ESP32-S3 and other variants).

The architecture should support additional MCU platforms.

### Platform-specific rules

2. Identify the SDK/HAL version.
3. Verify controller and target mode support.
4. Verify supported clock frequencies.
5. Check supported addressing modes.
6. Verify DMA and interrupt capabilities.

9. Check pin multiplexing and alternate functions.
10. Consult applicable silicon errata.

Do not invent hardware capabilities, register definitions, API functions or pin mappings.

## 3. I2C Protocol Fundamentals

Understand the following protocol concepts.

### Electrical signals

I2C normally uses two open-drain/open-collector signal lines:

- SDA: Serial Data.
- SCL: Serial Clock.

Both lines require appropriate pull-up arrangements.

Understand:

- Open-drain operation.
- Wired-AND behavior.
- Pull-up resistor sizing.
- Bus capacitance.
- Rise time and fall time.
- Logic voltage compatibility.
- Signal integrity.
- Clock stretching.
- Bus arbitration.

Never configure I2C SDA/SCL as ordinary push-pull outputs while operating as an I2C bus.

### Protocol conditions

Understand:

- START condition.
- STOP condition.
- Repeated START.
- Address phase.
- Read/write bit.
- ACK.
- NACK.
- Data transmission.
- Clock stretching.
- Arbitration loss.
- Bus busy condition.

A START condition is generated by SDA transitioning HIGH to LOW while SCL is HIGH.

A STOP condition is generated by SDA transitioning LOW to HIGH while SCL is HIGH.

Data should remain stable while SCL is HIGH, except when generating START and STOP conditions.

### Timing considerations

- SCL frequency.
- SCL high period.
- SCL low period.
- SDA setup time.

- STOP setup time.
- Bus rise time.
- Bus fall time.

The actual bus timing must satisfy all connected devices, not just the MCU.

Support applicable configuration parameters.

| Parameter | Description |
|---|---|
| Controller/target mode | Communication role |
| Clock frequency | 100 kHz, 400 kHz, 1 MHz, etc. |
| Addressing mode | 7-bit or 10-bit |
| Device address | Target address |
| Address direction | Read or write |

Separate bus-level configuration from device-specific configuration.

Do not treat every device as having an independent bus clock when devices share the same physical bus.

## 6. I2C Addressing

Understand:

### 7-bit addressing

The standard address space is 7 bits.

The transmitted address phase includes:

- 7-bit target address.
- 1-bit read/write direction.

Distinguish between:
- A 7-bit device address.
- An 8-bit address byte containing the direction bit.

Never accidentally shift an address twice or confuse address representations between MCU APIs.

### 10-bit addressing

Support when required and supported by the target MCU and device.

Understand its extended address sequence and compatibility requirements.

### Address validation

- Validate configured addresses.
- Reject reserved addresses where appropriate.
- Handle address NACK.
- Handle duplicate-address conflicts.
- Do not assume an ACK guarantees the correct physical device responded.

## 7. I2C Transaction Development

Implement reusable transaction primitives.

### 7.1 Write transaction

Typical operation:

START
-> Address + Write
-> ACK
-> Data bytes
-> ACK after each byte
-> STOP

### 7.2 Read transaction

Typical operation:

START
-> Address + Read
-> ACK
-> Receive data
-> Controller sends ACK for intermediate bytes
-> Controller sends NACK for final byte
-> STOP

### 7.3 Register write

Typical operation:

START
-> Address + Write
-> Register address
-> Data
-> STOP

### 7.4 Register read

Typical operation:

START
-> Address + Write
-> Register address
-> REPEATED START
-> Address + Read
-> Receive data
-> NACK
-> STOP

### 7.5 Combined transaction

Support write-then-read transactions without releasing the bus when the target device requires repeated START.

Do not replace repeated START with STOP + START unless the device protocol permits it.

### 7.6 Transaction considerations

Support, where applicable:

- Zero-length transfer validation.
- Single-byte transfers.
- Multi-byte transfers.
- Register-address widths of 8, 16 or other device-defined sizes.
- Configurable register-address byte order.
- Configurable transaction timeout.
- Repeated START.
- Multi-segment transactions.

Never assume all I2C devices use an 8-bit register address.

## 8. Controller and Target Architecture

### Controller mode

Support:

- Device addressing.
- Write operations.
- Read operations.
- Combined transactions.
- Bus arbitration.
- NACK detection.
- Timeout management.
- Bus recovery.

### Target mode

Where supported, consider:

- Own-address configuration.
- Address matching.
- Receive buffer management.
- Transmit buffer management.
- Clock stretching.
- Address-match interrupt.
- Repeated START handling.
- STOP detection.
- General Call handling, if required.

Target mode has different timing and buffer-management requirements from controller mode.

Do not implement target functionality using controller assumptions.

## 9. Transfer Mechanisms

Support applicable transfer methods.

### Polling

Suitable for:
- Low-frequency communication.
- Short transactions.
- Simple systems.
- Non-critical communication.

Consider:
- CPU blocking.
- Timeout behavior.
- Maximum blocking duration.

### Interrupt-driven

Suitable for:
- Asynchronous transaction completion.
- Event-driven communication.
- Systems where CPU blocking is undesirable.

Consider:
- ISR execution time.
- Interrupt priority.
- Transaction state management.
- Shared buffer ownership.
- Callback execution context.

### DMA

Suitable for:
- Larger data transfers.
- Reduced CPU overhead.
- Repeated or high-throughput communication.

Consider:
- DMA buffer lifetime.
- Buffer alignment.
- Cache coherency.
- Transfer completion.
- DMA errors.
- Peripheral interrupt coordination.

Do not assume DMA is beneficial for every small I2C transaction.

## 10. Error Handling and Diagnostics

Implement explicit error reporting.

| Error | Description |
|---|---|
| Address NACK | Target does not acknowledge address |
| Data NACK | Target does not acknowledge transmitted data |
| Bus busy | Bus remains occupied |
| Arbitration lost | Controller loses arbitration |
| Clock timeout | SCL remains in an unexpected state |
| Transaction timeout | Operation exceeds configured timeout |
| Bus error | Invalid bus condition detected |
| Overrun/underrun | Receive/transmit data handling failure |
| DMA error | DMA transfer failure |
| Invalid configuration | Unsupported or invalid parameters |
| Target not responding | Expected target does not respond |

Distinguish hardware errors from application-level communication errors.

### Error handling principles

1. Never wait indefinitely for hardware flags.
2. Implement bounded timeouts.
3. Preserve the original error cause.
4. Release hardware resources correctly.
5. Avoid silently ignoring NACK.
6. Do not blindly retry every error.
7. Define which errors are recoverable.
8. Avoid retry loops without a maximum retry count.
9. Report recovery failure separately from the original failure.
10. Ensure the bus is not left in an undefined software state.

## 11. I2C Bus Recovery

Bus recovery is essential for robust embedded communication.

Potential causes of a stuck bus:

- Target holds SDA LOW.
- Target is interrupted during a transaction.
- MCU resets during communication.
- Clock stretching is not released.
- Electrical noise causes communication failure.
- Peripheral state becomes inconsistent.

### Recovery strategy

1. Detect a stuck or busy bus.
2. Check SDA and SCL physical states where possible.
3. Determine whether recovery is permitted by the hardware and system design.
4. Disable the I2C peripheral if necessary.
5. Reconfigure pins according to the MCU documentation.
6. Attempt an appropriate recovery sequence if required.
7. Generate a STOP condition if possible.
8. Restore alternate-function configuration.
9. Reinitialize the I2C peripheral.
10. Verify that the bus returns to idle.
11. Report recovery success or failure.

Important:
- Do not blindly generate recovery clocks when another controller may own the bus.
- Follow the I2C specification and target-device recovery requirements.
- Recovery GPIO manipulation must not conflict with other peripheral owners.
- Never assume that nine clock pulses always recover every stuck bus.

## 12. Multi-Device Bus Management

Design for multiple target devices on one physical bus.

Consider:

- Device address management.
- Address conflicts.
- Different transaction formats.
- Device-specific timing requirements.
- Different register-address widths.
- Different transfer lengths.
- Bus ownership.
- Transaction scheduling.
- Bus locking.
- Device initialization order.

### Architectural rules

1. Separate bus instances from target-device instances.
2. Use one shared bus manager per physical I2C bus when needed.
3. Serialize controller transactions on a shared bus.
4. Prevent concurrent transactions from corrupting each other.
5. Define device-level transaction interfaces.
6. Avoid hardcoded addresses throughout application code.
7. Support device-specific timeouts where appropriate.
8. Avoid holding bus locks while performing unrelated application processing.

If multiple controllers share the bus, account for arbitration rather than assuming local software locking provides global ownership.

I2C Device Driver Layer:

- Device-specific command handling.

I2C Service / Bus Manager:
- Transaction management.
- Bus serialization.
- Timeout handling.
- Error recovery.
- Device management.

I2C Hardware Abstraction Layer:
- Initialization.
- Controller configuration.
- Transmit.
- Receive.
- Combined transfer.
- Interrupt handling.
- DMA handling.

MCU-specific Driver:
- STM32 HAL/LL or register-level implementation.

### Architecture rules

1. Keep application logic independent of MCU-specific APIs.
2. Keep device register definitions inside device drivers.
3. Separate bus-level and device-level configurations.
4. Define transaction ownership.
5. Define concurrency and locking behavior.
6. Use explicit timeout parameters.
7. Keep ISR processing minimal.
8. Avoid unnecessary dynamic allocation.
9. Make recovery behavior explicit.
10. Avoid unnecessary abstraction.

### C++ requirements

- Use explicit ownership.
- Use strongly typed device addresses and configurations where beneficial.
- Avoid unnecessary heap allocation.

### General requirements

- Follow project coding conventions.

5. SDA and SCL pin mapping.
6. Bus clock frequency.
7. Target device addresses.

10. Register-address widths.
11. Maximum transfer length.

13. Repeated START requirements.
14. Polling, interrupt or DMA requirements.
15. Timeout constraints.
16. Bus recovery requirements.
17. Concurrency requirements.
18. Electrical pull-up configuration.
19. Error reporting requirements.

Translate requirements into measurable and testable software requirements.

### Example requirements

**I2C_REQ_001 — Bus initialization**

The software shall initialize the specified I2C controller with the configured bus clock frequency and pin mapping.

**I2C_REQ_002 — Addressing**

The software shall support 7-bit target addressing for the configured I2C devices.

**I2C_REQ_003 — Data transmission**

The software shall support transmission of a configurable number of bytes to a specified target address.

**I2C_REQ_004 — Data reception**

The software shall support reception of a configurable number of bytes from a specified target address.

**I2C_REQ_005 — Combined transaction**

The software shall support a write-then-read transaction using a repeated START condition.

**I2C_REQ_006 — Timeout**

The software shall terminate an I2C transaction when its configured timeout expires.

**I2C_REQ_007 — NACK handling**

The software shall detect and report target address NACK conditions.

**I2C_REQ_008 — Bus recovery**

The software shall attempt bus recovery when a recoverable stuck-bus condition is detected.

**I2C_REQ_009 — Concurrency**

The software shall prevent overlapping transactions on the same controller instance.

**I2C_REQ_010 — Error reporting**

The software shall provide an identifiable error status for each failed transaction.

Specify timing, units, boundary behavior and recovery expectations explicitly.

## 17. Performance and Real-Time Analysis

Evaluate:

- Bus throughput.
- Transaction latency.
- CPU utilization.
- Interrupt frequency.
- DMA overhead.
- Bus occupancy.
- Lock waiting time.
- Timeout accuracy.
- Recovery duration.

### Basic I2C transfer calculation

For a transfer containing N data bytes using 7-bit addressing, a basic write transaction requires approximately:

`clock_cycles = 9 * (N + 1)`

This includes:
- One address byte.
- N data bytes.
- One ACK/NACK clock per byte.

For an idealized transaction:

`transfer_time = clock_cycles / SCL_frequency`

Actual transaction time is longer because of START/STOP timing, bus-free time, software overhead and possible clock stretching.

For combined transactions, account for additional address phases.

Do not assume the configured SCL frequency equals the effective application data throughput.
